## TL;DR

Strongest buildable idea today: **Repo-Specific Safety Harness for AI Coding Agents**. AI coding adoption is moving faster than trust, and the pain is not “does the model score well on benchmarks?” — it is “can this agent safely mutate *our* repo without skipping tests, violating policies, or creating review debt?” The wedge is a thin control/eval layer around real agent workflows before incumbents bake it in.

## Buildable Ideas

### Repo-Specific Safety Harness for AI Coding Agents

**Problem:** Teams adopting AI coding agents need repo-specific proof that agent changes are safe, correct, reviewable, and compliant with local engineering rules.

**What exists:** LangSmith and Braintrust cover LLM eval/observability; AI coding assistants are a proven paid market; AI code review tools like Codegen address PR review load; AppSec/governance platforms like Checkmarx cover scanning and policy enforcement; Fiddler and Coder are pushing agent guardrails, observability, auditability, and governance. Pricing was not provided in the research context.

**Who'd pay:** Engineering leaders, platform engineering teams, and developer productivity/security teams rolling out AI coding agents across real codebases, especially in larger or regulated organizations.

**The wedge:** Win by being the agent-agnostic safety and evaluation layer for a specific repo, not another generic LLM observability tool, code scanner, or review bot. The useful surface is the full coding-agent workflow: task → tool calls → repo mutations → tests → PR → rollback/replay.

**MVP:** Build a GitHub/GitLab + local agent wrapper that records every agent step: prompt/context, files touched, shell commands, tests run, diffs produced, and final PR. Add repo policies like “no migrations without approval,” “no secret access,” “must run these tests,” “no changes outside scoped directories,” and “block risky shell/network commands.” Generate an eval suite from failed PRs, reviewer comments, reverted commits, and test failures so teams can replay tasks across agents/prompts.

**Conviction:** medium — biggest risk is that this becomes a built-in governance feature inside coding-agent platforms, code review tools, or AppSec suites.

**Sources:** [Hacker News](https://news.ycombinator.com/item?id=48488990), [GitHub](https://github.com/mastra-ai/mastra/issues/18174), [GitHub](https://github.com/KittyCAD/modeling-app/issues/12196), [GitHub](https://github.com/fullsend-ai/fullsend/issues/2324)

### Protocol-aware observability for MCP servers

**Problem:** Generic APM turns MCP traffic into ordinary POSTs, hiding tool calls, retries, payload context, failures, and agent behavior.

**What exists:** Portkey MCP Gateway logs MCP requests, users, upstream servers, parameters, responses, timing, and errors; Azure API Management is adding packaging, observing, versioning, and governance for MCP servers; Obot frames MCP observability around tool invocations, policy decisions, sensitive data handling, latency, errors, and identity; ARMO argues generic APM/OpenTelemetry/logging miss MCP runtime behavior; Merge.dev describes visibility needs for MCP tool calls; Observe has an MCP server but not clearly an MCP-server observability product; LangSmith/Langfuse are adjacent LLM tracing tools. Pricing was not provided in the research context.

**Who'd pay:** AI platform engineers, developer-experience teams, and backend teams exposing internal or customer-facing MCP servers, especially teams already using Datadog/Grafana/OpenTelemetry but unable to debug agent tool-call behavior.

**The wedge:** Win as the narrow, developer-first MCP tracing layer that plugs into existing observability stacks instead of forcing teams into a full gateway or enterprise security platform. Reconstruct MCP semantics — tool calls, retries, payload context, errors, user/agent identity, and run timelines — then export clean OpenTelemetry-compatible traces.

**MVP:** Build a lightweight MCP observability proxy/SDK for TypeScript and Python MCP servers. Wrap or sit in front of an MCP server and emit protocol-aware traces: agent/session/user identity, server, tool name, redacted parameters, response/error payload, latency, retry grouping, and final outcome. Ship a simple timeline UI for one agent task plus OpenTelemetry export to Datadog/Grafana/Observe.

**Conviction:** medium — biggest risk is fast absorption by gateways, APM vendors, or LLM tracing platforms before this becomes a standalone system of record.

**Sources:** [Hacker News](https://spanly.com/)

### Durable Metrics Ingestion Buffer for Storage-Node Backpressure

**Problem:** Metrics ingestion clusters can collapse during storage-node restarts or slowdowns: rerouting amplifies load, while disabling rerouting can halt ingestion cluster-wide.

**What exists:** Kafka/Confluent are common durable ingestion backbones; AWS OpenSearch Ingestion added persistent buffering for downstream issues; Azure Data Explorer has queued ingestion; QuestDB documents ingestion buffers as a TSDB pattern; Fivetran, Airbyte, Stitch, Hevo, Matillion, Estuary Flow, NiFi, and Talend validate the broader ingestion market; Prometheus scaling patterns rely on remote_write and external systems like Thanos/Cortex. Pricing was not provided in the research context.

**Who'd pay:** SRE and observability platform teams running self-managed high-throughput metrics clusters, especially Prometheus-compatible or VictoriaMetrics-style deployments where storage-node restarts cannot cause ingestion loss.

**The wedge:** Win as the purpose-built reliability layer for metrics ingestion, not a generic ETL platform. Make it a small Prometheus/VictoriaMetrics-aware buffer deployable in one afternoon, with metric-specific semantics, replay throttling, tenant isolation, and restart runbooks.

**MVP:** Build a drop-in, disk-backed metrics ingestion proxy for Prometheus remote_write / OTLP metrics. Include durable local WAL, per-tenant queues, disk-budget retention, backpressure-aware replay, replay rate limiting after recovery, queue-depth/oldest-sample visibility, and a VictoriaMetrics-compatible deployment guide. Prove it by inducing vmstorage restarts/slowness and showing no ingestion outage or rerouting storm.

**Conviction:** medium — biggest risk is that users expect VictoriaMetrics/vminsert or Kafka to solve this, making the standalone product feel like an extra operational component.

**Sources:** [GitHub](https://github.com/VictoriaMetrics/VictoriaMetrics/issues/11125)

### Safe WASI Filesystem Layer for Wasm Embedders

**Problem:** Wasm embedders exposing filesystem-like APIs to untrusted guest code risk sandbox escapes through path resolution, symlinks, mount composition, permissions, or performance shortcuts.

**What exists:** Wasmtime validates the host-capability model but does not appear, from the provided context, to offer a packaged commercial VFS policy product; BrowserPod is a broader in-browser Wasm sandbox with Linux-compatible kernel/filesystem support; WebAssembly filesystem research/talks show technical interest; Cage and related sandbox-hardening content suggest extra layers may be needed. Pricing was not provided in the research context.

**Who'd pay:** Platform/security engineers at SaaS companies embedding untrusted Wasm plugins, backend/edge runtime teams, and AI-code-execution sandbox teams exposing limited filesystem access.

**The wedge:** Do not compete as a full Wasm runtime or Linux-in-Wasm environment. Win as the narrow, security-focused filesystem layer: a drop-in `wasi:filesystem` implementation with audited path semantics, mount policy composition, fuzz-tested escape prevention, and production integration examples.

**MVP:** Build an embeddable Rust-first WASI filesystem capability provider for Wasmtime/component hosts. Support read-only/read-write mounts, safe canonical path resolution, symlink policy, union/overlay mounts, deny-by-default permissions, and a conformance/fuzz suite for traversal and symlink escape cases. Ship OSS core plus paid hardening: audit reports, CI conformance tests, policy templates, and support.

**Conviction:** medium — biggest risk is that this sits too close to the runtime boundary and gets absorbed upstream by Wasmtime/WASI libraries or rebuilt in-house by security-sensitive buyers.

**Sources:** [GitHub](https://github.com/WebAssembly/WASI/issues/933)
